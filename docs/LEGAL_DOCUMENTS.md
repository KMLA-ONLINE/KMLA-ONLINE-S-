# 법률 문서 운영

이용약관·개인정보 처리방침·개인정보 안내 문구를 화면과 DB에 연결하는 방식과, 그 설계 근거와 개정 절차를 정한다. 사용자에게 보이는 동작은 [기능 명세 §4.7](functional-spec/accounts.md#47-이용약관과-개인정보-처리방침)이 소유하고, 문서 원문은 `legal/`이 소유한다.

## 1. 문서와 화면의 연결

| 문서                                              | 화면                                                                   |
| ------------------------------------------------- | ---------------------------------------------------------------------- |
| [이용약관](legal/terms_of_service.md)             | `/terms-of-service`가 원문을 그대로 그린다                             |
| [개인정보 처리방침](legal/privacy_policy.md)      | `/privacy-policy`가 원문을 그대로 그린다                               |
| [개인정보 안내 문구](legal/privacy_notice.md) 1항 | 가입 약관 단계의 `PrivacyNotice`가 원문을 그대로 그린다                |
| [개인정보 안내 문구](legal/privacy_notice.md) 2항 | 기존 회원 안내 `TermsAgreementDialog`. 문장이 같은지 테스트로 확인한다 |

안내 문구는 처리방침 2항의 표와 같아야 한다. 처리방침을 바꾸면 안내 문구도 함께 고친다. 안내 문구는 좁은 화면에서 가로로 밀리지 않도록 표 대신 목록으로 쓴다.

## 2. 개인정보 고지

서비스는 개인정보 처리에 동의를 받지 않는다. 필수 정보와 선택 정보 모두 이용계약 이행(「개인정보 보호법」 제15조제1항제4호)을 근거로 처리하므로 개인정보 수집·이용 동의 체크박스를 두지 않는다. 동의 체크박스를 두면 그 동의가 처리 근거처럼 보이게 되고, 철회 처리와 기록 의무가 생긴다. 그래서 개인정보 안내는 읽고 넘어가는 고지이며, 안내 화면의 버튼이나 체크박스를 "동의"로 표현하지 않는다. 다음 단계로 넘어가는 조건은 이용약관 동의뿐이다.

가입은 계정 → 약관 → 학교 프로필 → 이메일 인증 순서다. 계정 단계의 이메일·비밀번호는 이메일 인증 단계에 들어갈 때 처음 서버로 보내므로(§4.1), 학교 프로필을 받기 전에 둔 안내가 서버가 개인정보를 받기 전에 끝난다.

사용자 유형은 다음 단계에서 고르므로, 안내의 선택 정보 목록은 모든 유형의 항목을 보여 준다. 해당하지 않는 항목은 학교 프로필 화면에서 숨긴다.

## 3. 기존 회원 안내

약관 시행 전에 가입한 회원은 이용약관에 동의한 적이 없다.

- **이용약관**: 운영자와 회원 사이의 계약이므로 이 안내에서 동의를 받는다. 동의는 필수라 안내는 닫을 수 없고, 동의하지 않으면 로그아웃만 할 수 있다.
- **개인정보**: 생년월일·성별·계열은 필수로 받던 정보가 그대로 선택 정보로 바뀌어 계속 표시되므로 다시 동의를 받지 않는다. 바뀐 사실만 알린다.

안내 문구의 날짜는 약관과 처리방침이 처음 시행된 날(`TERMS_FIRST_EFFECTIVE_DATE`)이다. 이 안내를 보는 사람은 그날 전에 가입한 회원뿐이므로, 약관을 개정해도 그 회원에게 맞는 사실은 첫 시행이다. 동의 기록에는 동의한 시점에 시행 중인 판(`TERMS_VERSION`)을 남긴다.

## 4. 약관 판

이용약관의 판은 `legal/terms_of_service.md`의 시행일이다. 같은 값이 다음 두 곳에 있으며, 가입 신청과 동의 기록은 앱이 보낸 판이 DB의 판과 같을 때만 통과한다.

- 앱: `app/features/auth/model/terms.ts`의 `TERMS_VERSION`
- DB: `private.current_terms_version()` (`supabase/schemas/11-identity.sql`)

`test/features/auth/model/terms.test.ts`가 약관 원문의 시행일 두 곳, `TERMS_VERSION`, 스키마 함수의 날짜가 모두 같은지 확인한다. pgTAP 테스트는 날짜를 적지 않고 `private.current_terms_version()`을 읽는다.

### 개정 절차

1. `legal/terms_of_service.md` 머리의 시행일과 부칙의 시행일을 새 날짜로 바꾼다.
2. `supabase/schemas/11-identity.sql`의 `private.current_terms_version()`을 새 날짜로 바꾸고, [Database workflow](../supabase/README.md)대로 `npm run db:diff -- <name>`으로 migration을 만든다.
3. `TERMS_VERSION`을 새 날짜로 바꾼다. `TERMS_FIRST_EFFECTIVE_DATE`와 안내 문구 2항의 날짜는 바꾸지 않는다.
4. Vitest와 pgTAP을 돌린다.

개정 때는 다시 동의를 받지 않고 이용약관 제3조의 공지로 갈음한다(§4.7). DB가 앱보다 먼저 배포되므로, 새 판을 받기 전의 옛 앱은 가입 신청이 거절되고 새로고침 안내를 본다. 가입 도중 앱이 업데이트돼 초안의 판이 옛 판이면 인증 단계가 약관 단계로 되돌려 다시 동의받는다.
