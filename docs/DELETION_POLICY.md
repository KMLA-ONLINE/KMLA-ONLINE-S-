# 삭제 및 보존 정책

## 1. 한눈에 보기

| 데이터                | 언제 사라지나              | 방식                    | 상태 |
| --------------------- | -------------------------- | ----------------------- | ---- |
| 게시물                | 삭제 즉시                  | 하드 삭제               | 적용 |
| 첨부와 댓글 이미지    | 부모 삭제 즉시             | 하드 삭제               | 적용 |
| 댓글 (답글 없음)      | 삭제 즉시                  | 하드 삭제               | 적용 |
| 댓글 (활성 답글 있음) | 마지막 답글이 지워질 때    | 본문만 비우고 골격 유지 | 적용 |
| 반응                  | 취소 시, 부모 삭제 시      | 하드 삭제               | 적용 |
| 그룹                  | 삭제 즉시                  | 하드 삭제               | 적용 |
| 미발행 초안           | 생성 후 48시간             | 하드 삭제               | 적용 |
| 프로필 이미지         | 참조가 모두 사라진 뒤      | 참조 스윕               | 적용 |
| 계정 (탈퇴)           | 지우지 않는다              | 삭제 경로 없음          | 보류 |
| 시간표                | 계정과 함께                | 하드 삭제               | 적용 |
| 스토리                | 2일                        | 하드 삭제               | 적용 |
| 예약과 공강 일정      | 종료 후 2주                | 하드 삭제               | 적용 |
| 알림                  | 마지막 활동 후 30일        | 하드 삭제               | 적용 |
| 피드 세션             | 24시간                     | 하드 삭제               | 적용 |
| 피드 랭킹 이벤트      | 게시물과 함께, 또는 24시간 | 하드 삭제               | 적용 |
| 신고 기록             | 게시물과 함께              | 하드 삭제               | 적용 |
| 익명 활동 제재        | 지우지 않는다              | 영구 보존               | 보류 |

`적용`은 지금 스키마가 그렇게 동작한다는 뜻이다. `보류`는 정리 규칙을 두지 않기로 **결정한** 것이라 앞으로도 만들지 않는다. 이 문서가 정한 규칙은 §9의 순서대로 모두 구현되었다.

소프트 삭제가 남는 곳은 **활성 답글이 달린 댓글 하나뿐**이다. 그것도 본문을 비우고 트리 골격만 남긴다.

## 2. 이 문서의 범위

이 문서는 **행이 언제 사라지는가**를 정한다. 그 행이 가리키던 Storage object 파일을 누가 어떻게 지우는지는 [Storage 버킷 설계 §8.2](STORAGE_BUCKETS.md)가 소유하며 여기서 중복하지 않는다.

메시지(기능 명세 §13)는 테이블이 아직 없어 범위 밖이다. 구현할 때 §5에 절을 추가한다. 삭제된 메시지에 `삭제된 메시지입니다`를 남긴다는 요구(기능 명세 §18.3)는 §7.2의 댓글 자리 표시와 성격이 같으므로 그 규칙을 따른다.

## 3. 원칙

1. **기본은 하드 삭제한다.** 남길 이유를 대지 못하는 행은 남기지 않는다.
2. **소프트 삭제는 화면에 자리 표시가 필요할 때만 쓴다.** 자리 표시가 필요 없어지는 순간 그 행도 지운다. 소프트 삭제는 상태이지 종착지가 아니다.
3. **감사 로그를 목적으로 행을 남기지 않는다.** 운영 기록이 필요하면 별도의 설계 결정이며, 콘텐츠 테이블에 얹어 해결하지 않는다.
4. **사용자 행동이 계기면 즉시 지운다.** 시간이 계기인 것만 예약 작업으로 미룬다.
5. **행을 지우기 전에 object 경로를 같은 트랜잭션에서 큐에 넣는다.** 경로를 잃고 파일만 남는 순간을 만들지 않는다.
6. **배포 대상을 늘리지 않는다.** 정리 규칙이 늘어도 Edge Function은 추가하지 않고, Postgres 함수와 cron도 성격이 같으면 합친다. 배포 대상이 하나 늘면 시크릿·권한·관측 지점이 함께 늘어난다.

## 4. 삭제 계기

무엇을 즉시 지우고 무엇을 예약 작업에 넘길지는 **계기**로 가른다. 크기나 중요도로 가르지 않는다.

| 계기                 | 처리                                           | 예                    |
| -------------------- | ---------------------------------------------- | --------------------- |
| 사용자·운영자의 행동 | 그 트랜잭션에서 행을 지우고 경로를 큐에 넣는다 | 게시물·댓글·그룹 삭제 |
| 시간 경과            | cron이 기간이 지난 행을 지운다                 | 스토리, 예약, 알림    |
| 마지막 참조가 사라짐 | cron이 참조 집합의 여집합을 찾아 지운다        | 프로필 이미지         |

### 4.1 파일까지 수초 안에 사라진다

실제 파일은 Postgres가 지울 수 없고 Edge Function이 Storage API로 지워야 한다. 그렇다고 예약 실행을 기다리는 것은 아니다. `net.http_post`가 만드는 요청은 트랜잭션에 실려서, 롤백하면 나가지 않고 커밋하면 백그라운드 워커가 곧바로 보낸다. 그래서 삭제 RPC 하나가 다음을 한 트랜잭션에 담는다.

1. object 경로를 `private.storage_cleanup_queue`에 넣는다
2. 행을 하드 삭제한다
3. 큐를 드레인하도록 Edge Function 호출을 건다

1번은 **행 하나에 경로가 여럿일 수 있다**는 점에 주의한다. 사진 첨부는 원본과 축소본 두 개의
object를 가지므로(기능 명세 §18.6) 둘 다 같은 트랜잭션에서 큐에 들어가야 한다. 2번이 먼저
지나가면 남은 경로를 아무도 모르는 고아가 된다 — `thumbnail_path`가 행과 함께 사라지기 때문이다.

**원자성은 큐에서, 지연 시간은 3번에서** 얻는다. 호출이 실패해도 경로는 큐에 남아 백스톱 예약 작업이 회수한다. 게시물·댓글·그룹 삭제가 모두 이 경로를 쓴다. 왜 파일 삭제를 트랜잭션 안에 직접 넣지 않는지는 §8.1에 있다.

### 4.2 참조 스윕은 예외다

프로필 이미지는 슬롯에서 내려와도 그 변경 활동 게시물이 계속 참조한다. 마지막 참조가 사라지는 지점이 **슬롯 교체**와 **활동 게시물 삭제** 두 곳이라 즉시 삭제로 만들 수 없다. 두 지점에 같은 참조 검사를 심는 것보다 하나의 스윕이 판단하는 편이 정의를 한곳에 둔다. 자세한 것은 §7.3에 있다.

## 5. 도메인별 규칙

### 5.1 게시물과 댓글

| 대상                        | 규칙                                    | 상태 |
| --------------------------- | --------------------------------------- | ---- |
| `posts` (발행)              | 경로 큐잉 후 행을 즉시 하드 삭제        | 적용 |
| `posts` (미발행 초안)       | 생성 후 48시간 경과 시 예약 삭제        | 적용 |
| `post_attachments`          | 게시물과 함께 CASCADE. 단독 삭제도 즉시 | 적용 |
| `comment_images`            | 댓글 삭제·자리 표시 전환과 함께 즉시    | 적용 |
| `post_comments` (최상위)    | 서브트리를 통째로 하드 삭제             | 적용 |
| `post_comments` (자손 없음) | 즉시 하드 삭제                          | 적용 |
| `post_comments` (자손 있음) | 본문을 비우고 `deleted_at`을 세운다     | 적용 |
| 반응                        | 취소 시 즉시 삭제. 부모 삭제 시 CASCADE | 적용 |
| `private.post_authors` 등   | 부모 CASCADE                            | 적용 |

댓글만 소프트 삭제를 유지한다. 삭제된 댓글에 활성 답글이 남으면 대화 연결을 위해 `삭제된 댓글입니다` 표시를 유지해야 하기 때문이며(기능 명세 §9.4, §18.3), 이것은 로그가 아니라 제품 요구다.

자리 표시에 필요한 것은 트리 골격(`id`, `parent_comment_id`, `root_comment_id`, `depth`)뿐이다. 최대 5000자 본문을 자리 표시 하나 때문에 붙들고 있을 이유가 없으므로 **삭제 시점에 본문을 비운다.**

마지막 활성 자손이 삭제되면 그 자리 표시도 존재 이유를 잃는다. 이때 조상 방향으로 거슬러 올라가며 자리 표시만 남은 행을 함께 지운다. 그렇지 않으면 삭제만으로 이루어진 사슬이 영구히 남는다.

최상위 댓글을 지우면 답글 묶음 전체를 숨기므로 자리 표시가 필요 없다. 게시물도 마찬가지다. 기능 명세 §18.3은 삭제된 게시물을 "표시하지 않는다"고만 정하므로 행을 남길 근거가 없다.

### 5.2 그룹

| 대상                  | 규칙                                      | 상태 |
| --------------------- | ----------------------------------------- | ---- |
| `groups`              | 유예 없이 즉시 하드 삭제                  | 적용 |
| `group_media_objects` | 그룹 삭제·슬롯 교체 시 즉시 + 경로 큐잉   | 적용 |
| `group_memberships`   | 탈퇴·추방·그룹 삭제 시 즉시               | 적용 |
| `group_join_requests` | 승인·거절·취소·그룹 삭제 시 즉시          | 적용 |
| `group_categories`    | 즉시. 게시물의 `category_id`는 `SET NULL` | 적용 |
| `group_invites`       | 재발급 시 교체, 회수 시 즉시              | 적용 |

그룹 삭제는 소유자와 앱 관리자만 할 수 있고 확인 단계를 거치므로 유예 기간을 두지 않는다. 복구를 원하면 그룹을 다시 만든다.

### 5.3 프로필과 탈퇴

| 대상                    | 규칙                              | 상태 |
| ----------------------- | --------------------------------- | ---- |
| `profiles` (탈퇴)       | 삭제 경로를 두지 않는다           | 보류 |
| `profile_media_objects` | 참조 스윕 (§4.2)                  | 적용 |
| `profile_permissions`   | 권한 회수 시 즉시. 프로필 CASCADE | 적용 |
| `user_timetables`       | 보존 작업 없음. 프로필 CASCADE    | 적용 |
| 나머지 부속 테이블      | 프로필 CASCADE                    | 적용 |

시간표는 프로필당 한 행이고 `ON DELETE CASCADE`이므로 계정과 함께 사라진다. 무한히 자라지 않아 별도 정리 작업의 대상이 아니다.

**셀프 서비스 탈퇴는 만들지 않기로 했다.** `profiles.deleted_at` 컬럼과 `profile_status`의 `withdrawn` 값은 스키마에 있으나 이를 세우는 경로가 없고, 앞으로도 두지 않는다. 계정 행은 삭제되지 않으므로 프로필에 매달린 모든 테이블은 CASCADE 대상이 되지 않는다.

이 결정에는 법적 문서 쪽 숙제가 딸려 있다. 개인정보처리방침은 삭제·처리정지 요구를 받는 경로를 밝혀야 하는데, 셀프 서비스 탈퇴가 없으므로 그 경로는 **문의 창구로 접수해 운영자가 수동 처리하는 방식**이 된다. 처리방침을 다시 쓸 때 그 창구를 명시하고, 창구가 실제로 운영되어야 한다. 스키마가 아니라 문서와 운영의 몫이다.

기능 명세 §18.3도 이에 맞춰 셀프 서비스 탈퇴를 제공하지 않는다고 적고, `탈퇴한 사용자` 표시는 운영자가 정리한 계정에 적용된다고 밝힌다.

### 5.4 학교 부가 기능

| 대상                   | 규칙                                       | 상태 |
| ---------------------- | ------------------------------------------ | ---- |
| `stories`              | 본인 삭제·재작성 시 즉시. 2일 후 예약 삭제 | 적용 |
| `utility_reservations` | 미래 단발 예약 취소 시 즉시. 종료 후 2주   | 적용 |
| `gongang_schedule`     | 관리자 삭제 시 즉시. 2주 경과분 예약 삭제  | 적용 |

스토리는 당일분만 조회하므로(기능 명세 §17.6) 하루가 지나면 읽는 경로가 없다. 시간대 경계에서 잘리지 않도록 2일로 잡는다.

예약 보존은 2주다. 단발 예약은 `reservation_date`, 반복 예약은 `recurring_until` 기준으로 센다. 반복 예약은 종료일이 정해지기 전까지 지우지 않는다.

### 5.5 알림

| 대상                             | 규칙                                      | 상태 |
| -------------------------------- | ----------------------------------------- | ---- |
| `notifications`                  | `last_activity_at` 기준 30일 후 예약 삭제 | 적용 |
| outbox·시도 기록·이벤트 키       | 알림 CASCADE                              | 적용 |
| `private.web_push_subscriptions` | 구독 해제 시, `410 Gone` 응답 시 즉시     | 적용 |
| `post_id` / `comment_id` 외래 키 | `SET NULL`이 아니라 CASCADE               | 적용 |

게시물이 하드 삭제되면 그 게시물을 가리키던 알림은 이동할 곳이 없다. 현재 `SET NULL`은 링크가 끊긴 알림을 남기므로 CASCADE로 바꾼다. 운영 조치 알림(`post_moderated`)은 애초에 `post_id`를 싣지 않고 그룹 ID만 싣기 때문에, 바꾸어도 "내 글이 삭제되었다"는 알림은 사라지지 않는다.

`reservation_id`는 `SET NULL`을 유지한다. 예약 보존(2주)이 알림 보존(30일)보다 짧아 예약이 먼저 사라지는 구간이 생기며, 이때는 알림 본문을 두고 이동만 막는 편이 맞다.

### 5.6 피드 내부 상태

| 대상                                 | 규칙                                        | 상태 |
| ------------------------------------ | ------------------------------------------- | ---- |
| `private.feed_sessions` 및 하위      | 24시간 TTL. 프로필당 최신 7개 초과분은 즉시 | 적용 |
| `private.feed_bump_events`           | 게시물 CASCADE. 게시물당 최신 1건 외 삭제   | 적용 |
| `private.post_reaction_count_events` | 게시물 CASCADE. 24시간 경과분 삭제          | 적용 |

두 이벤트 테이블은 현재 삭제와 수정이 트리거로 전면 차단되어 있고 외래 키에 `ON DELETE` 절이 없다. **이것이 게시물 하드 삭제를 막는 유일한 구조적 제약이다.** 외래 키를 CASCADE로 바꾸고 트리거는 §7.4의 가드를 확인하도록 완화한다.

보존 기간의 근거는 랭킹이 실제로 읽는 범위다. 반응 이벤트는 **발행 후 6시간 이내 게시물에만** 합산되므로 그보다 오래된 이벤트는 어떤 조회에도 잡히지 않는다. `#업` 이벤트는 게시물당 가장 최근 1건만 읽고, 1시간 중복 방지 검사도 최근 구간만 본다. 나머지는 죽은 데이터다.

### 5.7 운영과 모더레이션

| 대상                                            | 규칙               | 상태 |
| ----------------------------------------------- | ------------------ | ---- |
| `private.group_post_reports` 및 무시 기록       | 게시물과 함께 삭제 | 적용 |
| `private.group_anonymous_activity_restrictions` | 지우지 않는다      | 보류 |
| `private.storage_cleanup_queue`                 | 처리 완료 시 즉시  | 적용 |
| `private.storage_cleanup_runs`                  | 30일               | 적용 |

신고 기록은 게시물이 하드 삭제되면 외래 키 CASCADE로 사라진다. 지금은 `deleted_at`이 세워질 때 트리거가 지우고 있으나, 게시물이 즉시 하드 삭제로 바뀌면 그 트리거는 불필요해진다.

익명 활동 제재는 **정리 규칙을 두지 않는다.** 제재는 드물게 일어나고 한 건이 행 하나이며 기간 상한이 180일이라, 영구히 쌓아도 누적 비용이 사실상 없다. 정리 작업을 만들 이유보다 만들지 않을 이유가 크다. 제재 종료 뒤의 문의에 답할 수 있다는 것도 덤이다.

## 6. 예약 작업

정리 목적의 cron은 아래가 전부다. 새 보존 규칙이 생겨도 잡을 늘리지 않고 성격이 같은 함수에 합친다.

| cron                                   | 주기         | 하는 일                                     | 상태 |
| -------------------------------------- | ------------ | ------------------------------------------- | ---- |
| `enqueue-storage-cleanup-daily`        | 매일 03:17   | 방치된 초안·업로드, 참조 없는 프로필 이미지 | 적용 |
| `drain-storage-cleanup-hourly`         | 매시간       | 백스톱. 깨우기가 놓친 큐를 회수             | 적용 |
| `sweep-unreferenced-storage-weekly`    | 일요일 04:41 | 2층 안전망. 참조 없는 object 탐색           | 적용 |
| `reconcile-storage-cleanup-runs`       | 5분마다      | `pg_net` 응답을 실행 기록에 맞춤            | 적용 |
| `cleanup-expired-feed-sessions-hourly` | 매시 23분    | 만료된 피드 세션                            | 적용 |
| `cleanup-notifications-daily`          | 매일 04:23   | 30일 지난 알림                              | 적용 |
| `cleanup-expired-records-daily`        | 매일         | 스토리·예약·공강 일정·피드 이벤트 보존      | 적용 |

`enqueue-storage-cleanup-daily`는 역할이 줄어든다. 지금은 tombstone된 첨부와 미디어까지 훑지만, 그 삭제가 즉시로 옮겨 가면 **계기가 시간뿐인 것**만 남는다. 창을 닫아 버린 업로드와 방치된 초안이 그렇다.

드레인은 예약 실행이 주 경로가 아니다. 삭제 RPC가 커밋 직후 워커를 깨우므로(§4.1) 대부분의 파일은 예약 실행을 기다리지 않는다. 하루 한 번을 매시간으로 올리는 것은 깨우기가 실패했거나 100건 한도에 걸려 남은 분량을 회수하기 위해서다. 폴링이 아니라 백스톱이다.

백스톱을 자주 돌리기 위해 `private.invoke_storage_cleanup()`은 **큐가 비어 있으면 HTTP 호출과 실행 기록을 건너뛴다.** 부를 때마다 `private.storage_cleanup_runs`에 한 행씩 남기던 예전 동작 그대로 매시간 돌리면, 빈 실행 기록이 쌓여 관리자 화면의 마지막 실행 결과가 무의미해지기 때문이다.

### 6.1 이 변경이 늘린 배포 대상

| 종류          | 추가 | 내용                                                         |
| ------------- | ---- | ------------------------------------------------------------ |
| Edge Function | 0    | 기존 `cleanup-storage-objects`를 그대로 쓴다                 |
| Postgres 함수 | 2    | `private.purge_posts()`, `private.cleanup_expired_records()` |
| cron          | 1    | `cleanup-expired-records-daily`                              |

깨우기는 Edge Function을 새로 만들지 않는다. `pg_net`으로 **이미 배포된** `cleanup-storage-objects`를 부르는 것뿐이다. 보존 작업도 순수 SQL이라 배포 없이 마이그레이션으로 들어간다.

Postgres 함수도 최소로 잡는다. 조용한 깨우기는 새 함수를 만드는 대신 `private.invoke_storage_cleanup()`에 파라미터를 더해 한 함수가 두 호출자를 받는다. 피드 이벤트 가드도 보조 함수를 두지 않고 트리거 함수가 세션 설정을 직접 읽는다. 다만 파라미터 추가는 시그니처 변경이라 함수 drop·recreate와 `EXECUTE` 권한 재부여가 뒤따르므로, 생성된 마이그레이션에서 그 부분을 반드시 확인한다.

`private.purge_posts()`는 예외로 둔다. 게시물 삭제는 그룹 게시물·개인 게시물·그룹 삭제 세 곳에서 일어나고 세 곳이 **같은 순서**(가드 세우기 → 경로 큐잉 → 행 삭제 → 워커 깨우기)를 지켜야 한다. 순서를 하나라도 뒤집으면 경로를 잃고 파일이 영구히 남으므로, 스무 줄을 세 번 베끼는 것보다 한곳에 두는 편이 안전하다.

스토리·예약·공강 일정·피드 이벤트는 계기가 모두 "시간 경과"로 같아서 함수 하나에 넣는다. 넷을 각각 만들면 cron 넷과 함수 넷이 되고, 관리자 화면에서 확인할 지점도 넷이 된다.

## 7. 지켜야 할 예외

### 7.1 `#업` 댓글은 삭제할 수 없다

피드 순위를 올린 `#업` 댓글은 작성자도 지울 수 없다. 지우고 다시 달아 순위를 반복해 올리는 것을 막기 위해서다. 이 규칙은 `delete_post_comment`의 명시적 검사가 담당하며, §5.6에서 append-only 트리거를 완화해도 영향받지 않는다. 두 장치는 목적이 다르다.

게시물 자체가 삭제되면 그 아래 `#업` 댓글도 함께 사라진다. 이 제약은 살아 있는 게시물의 순위를 지키려는 것이지 행을 영구 보존하려는 것이 아니다.

### 7.2 댓글 자리 표시는 골격만 남긴다

`삭제된 댓글입니다` 자리 표시에는 본문과 작성자를 노출하지 않는다(기능 명세 §9.4). 따라서 자리 표시로 남는 행은 본문이 비워진 상태여야 한다. 비우지 않고 화면에서만 감추는 방식은 이 정책에 어긋난다.

### 7.3 프로필 이미지는 참조가 사라진 뒤에 지운다

프로필 이미지를 교체해도 이전 이미지는 그 변경 활동 게시물이 살아 있는 동안 남는다. 활동 게시물이 그 시점의 이미지를 계속 가리키기 때문이다. **슬롯 교체는 삭제 계기가 아니다.**

게시물이 하드 삭제로 바뀌면 `private.referenced_storage_objects` 뷰의 활동 게시물 조건에서 `deleted_at` 검사를 걷어낸다. 행이 없으면 참조도 없기 때문이다. 이 뷰는 살아 있는 object의 유일한 정의이므로, 바꾸는 변경에서 pgTAP 테스트를 함께 고친다.

### 7.4 피드 이벤트는 정리 경로에서만 지울 수 있다

`feed_bump_events`와 `post_reaction_count_events`의 append-only 트리거는 유지하되, 세션 로컬 설정을 확인해 정리 경로만 통과시킨다. 트리거 함수가 그 설정을 직접 읽으므로 보조 함수는 두지 않는다. CASCADE 삭제도 이 트리거를 거치기 때문에, 가드 없이는 게시물을 지울 수 없다.

두 테이블은 `private` 스키마에 있고 RLS 거부 정책이 걸려 있으며 `authenticated`에 권한이 없다. 클라이언트는 애초에 이 행을 건드릴 수 없고, 트리거는 정의자 권한 함수의 실수를 막는 2차 방어선이다.

## 8. 설계 근거

### 8.1 파일 삭제를 트랜잭션에 넣지 않는 이유

행은 즉시 지우면서 파일만 큐에 맡기는 것은 타협이 아니다. 세 가지 대안이 모두 더 나쁘다.

- **클라이언트가 Storage를 직접 지운다.** 어떤 버킷에도 클라이언트 DELETE 정책을 두지 않는다는 원칙과 충돌한다. object 수명을 클라이언트가 쥐면 삭제 도중 창을 닫은 사용자가 고아 파일을 남기고, 권한을 넓히면 남의 파일을 지울 길이 열린다.
- **삭제 트랜잭션 안에서 Storage API를 호출한다.** `pg_net`은 비동기라 트랜잭션 안에서 결과를 알 수 없다. 안다 해도 삭제 성공 여부가 외부 서비스 응답에 묶이고 네트워크 I/O 동안 행 잠금을 쥔다. 실패하면 되돌리거나 오류를 삼켜야 하는데, 후자는 **기록조차 없는 고아**라 큐보다 나쁘다.
- **Edge Function이 파일과 행을 차례로 지운다.** 두 시스템에 걸친 2단계 삭제라 원자성이 없다. 파일만 지워지고 행이 남으면 **게시물은 살아 있는데 이미지가 깨진다.** 큐 방식의 실패는 항상 "행은 사라졌고 파일이 잠시 남는다" 한 방향이며 재시도로 수렴한다.

### 8.2 워커 깨우기의 주의점

- **호출 실패가 삭제를 실패시키면 안 된다.** `private.invoke_storage_cleanup()`은 Vault 설정이 없으면 예외를 던진다. 이를 그대로 삭제 RPC에서 부르면 설정 문제로 **게시물이 지워지지 않는다.** 그렇다고 예외를 없앨 수도 없다. 설정 누락을 조용히 넘기지 않는 것이 그 예외의 목적이기 때문이다. 함수를 새로 만드는 대신 **파라미터로 호출자를 구분한다.** 예약 경로는 지금처럼 예외를 던지고, 삭제 RPC가 부를 때는 오류를 삼킨다(§6.1).
- **연속 삭제를 디바운스한다.** 진행 중인 실행이 있으면 새로 부르지 않는다. 게시물 열 개를 잇달아 지워도 호출은 한 번이면 된다.
- **한 번의 호출이 큐를 다 비우지 못한다.** 워커는 claim 한 번에 최대 100건을 가져가고 루프를 돌지 않는다. 첨부가 많은 게시물을 연달아 지우면 남는 분량이 생기므로, 워커가 스스로 다시 호출하거나 백스톱이 흡수해야 한다.

### 8.3 피드 이벤트 가드를 명시적으로 두는 이유

`pg_trigger_depth()`로 CASCADE만 구분하는 방법은 쓰지 않는다. 보존 작업이 이벤트를 직접 지울 때는 깊이가 0이라 어차피 통과시킬 방법이 필요하고, 조건이 둘로 갈리면 의도가 코드에서 사라진다. 세션 로컬 설정 하나로 통일하며, 그 설정을 읽는 보조 함수는 만들지 않는다(§3 원칙 6).

## 9. 구현 기록

각 단계는 `supabase/schemas/`를 먼저 고치고 마이그레이션 초안을 생성해 전문을 검토한 뒤, pgTAP 테스트를 같은 변경에 넣었다. 아래 순서대로 모두 적용되었다.

1. **피드 이벤트 잠금 해제** (§5.6, §7.4) — 외래 키 CASCADE와 가드 도입. 이것이 열리지 않으면 2·5·6이 외래 키 위반으로 막혔다. 반응 취소 이벤트를 남기던 트리거도 같은 가드를 보게 고쳤다. 그러지 않으면 게시물을 지울 때 CASCADE가 이미 사라진 게시물을 가리키는 이력을 넣으려다 실패한다.
2. **깨우기 도입과 백스톱 전환** (§4.1, §6, §8.2) — 2단계로 앞당겼다. 아래 3단계의 삭제 경로가 이 깨우기를 그대로 쓰기 때문이다.
3. **게시물 하드 삭제** (§5.1) — `posts.deleted_at` 제거. 조회 필터, 발행 시각 검사 제약, 부분 인덱스, 신고 정리 트리거, 댓글 이미지 tombstone 트리거가 함께 사라졌다. Storage 정책과 `referenced_storage_objects` 뷰는 컬럼을 붙들고 있어 제거 앞에서 다시 정의해야 했고, 이미 소프트 삭제된 게시물은 같은 마이그레이션이 먼저 지웠다.
4. **알림 외래 키 전환** (§5.5).
5. **댓글 하드 삭제와 본문 비우기** (§5.1, §7.2).
6. **그룹 즉시 삭제** (§5.2) — 삭제 알림이 그룹 이름을 조회로 얻고 있어 제목에 싣도록 바꾸고, 트리거에서 `delete_group` 안으로 옮겼다.
7. **보존 작업 통합** (§5.4, §5.6) — `cleanup-expired-records-daily` 신설.

탈퇴(§5.3)와 익명 활동 제재 정리(§5.7)는 만들지 않기로 했으므로 이 목록에 없다.

기능 명세도 함께 고쳤다. §8.12(게시물 삭제)와 §18.3(콘텐츠 보존)이 삭제를 표시 규칙으로만 적고 있어 저장을 멈춘다는 사실을 담도록 바꾸었고, §18.3의 탈퇴 문장은 셀프 서비스 탈퇴를 제공하지 않는다는 서술로 바꾸었다. [Storage 버킷 설계 §8.2](STORAGE_BUCKETS.md)의 1층 서술은 tombstone 단계가 사라진 만큼 아직 갱신이 남아 있다.
