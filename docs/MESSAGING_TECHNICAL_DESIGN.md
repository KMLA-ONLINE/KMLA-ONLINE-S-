# 메시지 기술 설계

> **상태**: 구현(`supabase/schemas/71-messaging.sql`). 기간을 정한 대화 알림 끄기는 아직 없다.

이 문서는 [메시지 기능 명세](functional-spec/messaging.md)를 구현하기 위한 데이터, 암호화, 동기화와 전달
경계를 정의한다. 제품 동작은 기능 명세가 정본이다. 메시지 Push 전달은
[알림 및 Web Push 기술 설계](NOTIFICATION_TECHNICAL_DESIGN.md) §11, 첨부 버킷은
[Storage 버킷 설계](STORAGE_BUCKETS.md) §4.4를 따른다.

## 1. 원칙

- 브라우저는 평문으로 보내고 평문으로 받는다. 클라이언트 암호화, 대화별 키, 키 브로커 Edge Function은 두지
  않는다.
- 메시지 본문과 첨부 원본 파일 이름은 Postgres 안에서 서비스 키 하나로 암호화해 저장한다(§4).
- 메시지 행에는 client grant를 주지 않는다. 읽기와 쓰기는 모두 호출자를 검증하는 `security definer` RPC로만
  한다. 복호화가 RPC 안에서만 일어나야 하기 때문이다.
- 볼 수 있는 메시지의 범위는 멤버십의 참여 기간으로 서버가 정한다. 클라이언트 필터는 UX일 뿐이다.
- 목록과 대화방은 한 화면에 set-based RPC 하나를 쓴다. 대화마다, 메시지마다 따로 요청하지 않는다.

## 2. 데이터 모델

- `public.conversations`: 유형(`direct`·`group`), 그룹 이름, 생성자, 마지막 메시지 시각. 1:1 대화는 두
  프로필 쌍에 unique 제약을 두어 같은 두 사람 사이에 하나만 존재하게 한다.
- `public.conversation_members`: 대화, 프로필, 참여 시각(`joined_at`), 나간 시각(`left_at`), 스스로 나갔는지
  (`left_by_self`), 읽음 위치, 알림 끄기 만료 시각, 멘션만 알릴지(`mentions_only`, §8). 대화 목록과 탭 배지는 가장 최근 기간을 스스로 나간 대화를
  빼고, 대화 ID를 지정한 한 건 조회는 그대로 돌려준다. 내 목록에서 숨긴 시각(`hidden_at`, 기능 명세 §13.23)도
  가장 최근 기간에 두며, 목록과 탭 배지는 숨긴 뒤로 사람이 보낸 메시지가 없는 대화를 같은 방식으로 뺀다. 숨긴
  대화를 대화 ID로 직접 열면 클라이언트가 숨김을 푼다. 다시 참여하면 새 참여 기간 행을 만들어 이전 기간과 사이 기간을 구분한다. 그룹
  최대 100명은 멤버 추가 RPC가 대화 행을 잠근 뒤 강제한다.
- `private.messages`: 대화, 발신자, `sent_at`, 답장 대상, 본문 암호문, 키 버전, 편집 시각, 삭제 시각,
  시스템 메시지 종류, 멘션 대상(§8). 클라이언트가 만든 UUID를 기본 키로 받아 재전송을 멱등으로 만든다.
- `private.message_attachments`: 메시지, 버킷, object path, MIME type, 크기, 이미지 치수, 파일 이름
  암호문과 키 버전. 상태는 다른 첨부와 같은 prepare-upload-finalize를 따른다(Storage 설계 §7).
- `private.message_reactions`: 메시지와 프로필 기준 한 행. `private.message_pins`: 고정은 대화 전체의
  상태이므로 메시지 기준 한 행에 고정한 사람과 시각을 둔다. 둘 다 평문이므로 암호화하지 않지만, 메시지를
  볼 수 있는 사람만 보도록 메시지와 같은 RPC 경계 안에 둔다.

볼 수 있는 메시지는 "읽는 사람의 참여 기간 중 하나에 `sent_at`이 들어가는 메시지"다. 새 멤버의 참여 이전
메시지와 나간 멤버의 이후 메시지는 이 조건 하나로 함께 막는다. 첨부 object의 Storage RLS도 같은 조건을
쓴다.

삭제는 메시지 행을 남기고 본문 암호문, 첨부, 반응을 지운 뒤 삭제 시각을 기록한다. 답장 인용이 원본 행을
가리키므로 행 자체는 지우지 않는다.

## 3. 공개 API

클라이언트는 다음 authenticated RPC만 사용한다. 이름은 구현 시 확정한다.

- 대화 목록: 내 대화와 마지막 메시지 미리보기(복호화), 읽지 않은 수, 알림 상태를 한 번에 반환한다.
- 대화방 열기: 대화 정보, 최신 메시지 한 페이지와 그 앞 커서, 고정 메시지 전체를 함께 받는다. 대화
  정보는 대화 목록 RPC에 대화 ID를 주어 한 건만 읽고, 메시지 페이지 RPC와 동시에 부른다. 고정 메시지와
  답장 원문은 아직 불러오지 않은 페이지에 있을 수 있어 페이지와 따로 준다.
- 메시지 페이지: `(sent_at, id)` 커서로 이전 메시지를 한 페이지씩 반환한다. 커서 행을 찾지 않고
  비교로 자르므로 커서의 메시지가 사라져도 결과가 어긋나지 않는다. 반응 집계, 내 반응, 고정 여부,
  답장 원문의 발신자와 본문 일부를 함께 붙여 행마다 추가 조회가 없게 한다.
- 새 메시지 따라잡기: 마지막으로 본 `changed_at` 이후에 새로 오거나 바뀐 메시지를 반환한다(§5).
- 전송, 편집(15분), 삭제, 반응 설정·제거, 고정·해제, 읽음 위치 갱신.
- 대화 생성, 그룹 이름 변경, 멤버 추가·나가기, 소유주의 그룹 삭제, 대화 알림 설정. 그룹 삭제는 지우기 전에
  현재 멤버에게 `conversation_deleted` 신호를 보내고, 첨부 object 경로를 정리 큐로 옮긴 뒤 대화를 지운다.
- 대화 내 검색(§6).

모든 RPC는 `search_path = ''`, 기본 `EXECUTE` 회수, `authenticated`에만 grant를 둔다. 길이, 편집 기한,
삭제된 메시지에 대한 답장 금지, 그룹 인원 상한은 RPC와 제약조건이 강제한다.

## 4. 암호화

- 키는 Supabase Vault의 secret 하나다. RPC가 호출당 한 번 `vault.decrypted_secrets`에서 읽어 변수에 두고
  그 호출이 다루는 모든 행에 쓴다.
- 암호화는 pgcrypto `pgp_sym_encrypt(본문, 키, 's2k-mode=1, cipher-algo=aes256')`다. 키가 무작위
  고엔트로피 값이므로 비밀번호용 반복 키 유도는 끄고(`s2k-mode=1`), PGP 형식의 변조 검사(MDC)를 쓴다.
  로컬 측정에서 반복 키 유도를 켜면 한 건 복호화에 약 0.3ms, 끄면 1,000건에 약 7ms였다. pgsodium은
  Supabase에서 deprecated이므로 쓰지 않는다.
- 각 암호문 옆에 키 버전을 저장한다. Vault 이름은 `message_key_v<버전>`이고 가장 큰 버전으로 쓴다. 키를
  교체하면 새 버전을 추가하고, 이전 버전 secret은 남은 행을 다시 암호화할 때까지 복호화용으로 유지한다.
  환경별 설정은 `supabase/README.md`의 Vault 절에 있다.
- secret 값은 migration과 저장소에 넣지 않는다. 환경마다 한 번 만들고, 로컬은 `supabase/seed.sql`이 개발용
  값을 만든다.
- 평문은 RPC 인자와 반환값으로만 지나간다. 함수 오류 메시지, `raise` 로그, Realtime payload, Push outbox에
  평문을 남기지 않는다.

보장 범위는 기능 명세 §13.20과 같다. 테이블, 백업, 로그를 직접 봐도 평문이 없지만, `postgres`나 service
role로 SQL을 실행할 수 있는 사람은 Vault를 거쳐 복호화할 수 있다.

## 5. Realtime과 클라이언트 동기화

메시지 행은 client grant가 없고 암호문이므로 Postgres Changes로 내려보내지 않는다. 메시지 변경
trigger가 `realtime.send`로 현재 멤버마다 자기 private Broadcast topic(`messaging:<profile_id>`)에
"무엇이 바뀌었는지"만 보낸다. payload에는 대화와 메시지 ID만 넣고 본문은 넣지 않는다. 클라이언트는 셸에서
채널 하나만 구독하고, `realtime.messages` RLS는 topic이 호출자의 것인지만 확인한다. 대가로 메시지 하나가
바뀔 때 현재 멤버 수만큼 신호가 나간다. 대화 목록과 탭 배지가 이 신호를 쓰므로 방을 열지 않은 멤버도
받아야 한다.

- `message_changed`: 메시지가 새로 오거나 바뀌었다. 수정, 삭제, 반응, 고정은 메시지의 `changed_at`을
  갱신하므로 모두 이 신호 하나로 온다. `kind`가 `content`(새 메시지, 수정, 삭제)일 때만 대화 목록을 다시
  읽고, 반응·고정(`meta`)은 열린 대화방만 따라잡는다.
- `read_changed`: 다른 멤버가 읽음 위치를 옮겼다. 메시지의 읽지 않은 수는 `changed_at`에 잡히지 않으므로
  열린 대화방의 최근 메시지만 `list_message_read_counts`로 다시 받는다. 읽지 않은 수는 보낸 사람과 호출자를
  빼고 세므로 그룹의 상대 메시지에도 의미가 있다. 본문은 다시 복호화하지 않는다. 이 수는 방을 연 사람만
  그리므로 멤버마다 보내지 않고 대화방 topic(`messaging-room:<conversation_id>`)으로 한 번 보낸다. 멤버마다
  보내면 방을 연 사람이 읽을 때마다 멤버 수만큼 신호가 나가 그룹 하나의 메시지 하나에 멤버 수의 제곱에 가까운
  신호가 쌓인다. 클라이언트는 열린 대화방마다 그 topic을 구독하고 닫으면 끊으며, RLS는 호출자가 그 대화의
  현재 멤버인지 확인한다. payload의 읽은 사람이 나면 거른다. Realtime은 권한을 채널에 붙을 때 확인하므로
  방을 연 채 내보내진 멤버는 다시 붙기 전까지 대화와 읽은 사람의 ID만 더 받는다.
- `typing`: 1:1 상대의 입력 상태(기능 명세 §13.27). 다른 신호와 달리 DB trigger를 거치지 않고 클라이언트끼리
  전용 topic(`messaging-typing:<conversation_id>`)으로 주고받으며 저장하지 않는다. 보내기 권한이 필요한데
  대화방 topic에 열면 멤버가 `read_changed`를 위조할 수 있어 topic을 나눴고, 이벤트별 제한은 쓰지 않는다. 입력하는
  동안 3초에 한 번 보내고 받는 쪽은 5초 뒤 지운다. 신호마다 Realtime 메시지로 과금되어(받는 사람 수 + 1) 그룹은
  topic을 열지 않으며, RLS도 1:1 대화만 허용한다. 그룹을 추가하려면 비용을 먼저 다시 따진다.
- 운영 작업의 대량 갱신은 `messaging.suppress_signals`로 신호와 `changed_at` 갱신을 끈다
  (`supabase/README.md`).

클라이언트는 신호를 받으면 열린 대화방만 따라잡기 RPC(`list_message_changes`)로 마지막으로 본
`changed_at` 이후의 메시지를 받아 Query cache에 합치고, 대화 목록은 무효화한다. 늦게 커밋된 트랜잭션은
그보다 앞선 시각으로 기록될 수 있어 서버가 10초를 겹쳐 읽고, 겹친 행은 같은 ID로 덮는다. 내 변경 요청이
진행 중인 메시지와 cache보다 낡은 행은 덮지 않는다. 한 번에 받을 수 있는 수를 넘으면 최신 페이지부터 다시
읽되 전송 중인 내 메시지는 남긴다. 채널(내 topic과 열린 대화방 topic)이 처음 붙거나 다시 붙을 때, 창으로 복귀할 때 같은 RPC로 빈
구간을 메우고, 실패하면 간격을 늘리며 몇 번 다시 시도한다. 창 복귀는 직전 맞춤 뒤 30초가 지났을 때만
맞춘다. 메시지 신호와 1:1의 읽음 신호는 150ms 동안 모아 한 번에 처리한다. 그룹의 읽음은 첫 신호를 같은 시간 뒤에
처리하고 그 뒤로는 1초에 한 번만 다시 받는다. 그룹에서는 멤버가 읽을 때마다 방을 연 모두가 읽음 수를 다시 받기
때문이다. 신호를 놓쳐도 따라잡기가 정답을 돌려주므로 Broadcast는 지연을 줄이는 수단이지 정본이 아니다.

- 대화 목록과 각 대화의 메시지 페이지는 [클라이언트 데이터 캐시 정책](DATA_CACHE_POLICY.md)의 키 규칙을
  따르는 별도 쿼리로 둔다. 대화방 메시지는 infinite query로 이전 페이지를 이어 붙이고, 이전 페이지를 붙일
  때 스크롤 위치를 보존한다.
- 전송은 클라이언트 UUID로 낙관적 행을 먼저 넣고, 성공하면 서버 행으로 교체한다. 실패하면 그 행을 거두고
  작성창이 비어 있으면 보내려던 입력을 되살린다. 같은 UUID 재전송은 서버가 한 번만 저장한다.
- 반응, 고정, 편집, 삭제도 낙관적으로 반영하고 실패하면 되돌린다.
- 다시 들어온 대화방은 대화 목록의 그 대화와 메시지·고정 cache가 남아 있으면 서버를 기다리지 않고 그것으로
  연다. 닫힌 방은 따라잡지 않으므로, 방이 열리면 마지막으로 본 변경 이후를 따라잡기로 받는다. 처음 열 때처럼
  최신 페이지부터 시작하도록 앞선 페이지는 버리고, 다시 보낼 원본 파일이 사라진 보내지 못한 첨부 메시지도
  거둔다. 하나라도 cache에 없으면 대화 정보, 최신 페이지, 고정 메시지를 함께 읽는다.
- 대화방이 화면에 보이고 창에 포커스가 있는 동안 가장 최근의 상대 메시지까지 읽음 위치를 갱신하고, 목록의 그 대화 읽지 않은
  수를 먼저 0으로 그린다. 마지막 메시지가 내 메시지여도 그 앞의 상대 메시지를 기준으로 한다. 이 갱신이 메시지
  Push 억제의 근거다(알림 기술 설계 §11). 서버는 읽음 위치를 옮겼는지 돌려주며, 옮기지 않았고 목록도 이미
  읽음이었으면 목록과 탭 배지를 다시 읽지 않는다.
- 맨 아래를 보고 있을 때 새 메시지가 붙으면 따라 내려가고, 지난 대화를 보던 중이면 위치를 지킨다.
- 응답을 잃어 실패로 보인 전송을 같은 내용으로 다시 보내면 같은 ID를 써서 서버가 한 번만 저장한다.
- `send_message`는 기본으로 보낸 사람의 읽음 위치를 보낸 메시지로 옮긴다. 방을 열지 않고 보내는 게시물
  공유(기능 명세 §8.13)는 `p_mark_read = false`로 보내 그 방의 안 읽은 메시지와 배지를 남긴다. 공유도
  다시 보내기 사이에 대화별 메시지 ID를 기억해 응답을 잃은 전송이 두 번 저장되지 않게 한다.
- 화면용 문자열(시각, 날짜 구분, "12분" 같은 상대 시간)은 서버가 주지 않는다. RPC는 `timestamptz`를
  반환하고 `model/`이 표시 문자열과 묶음 경계를 계산한다. 내 메시지 판정은 셸 프로필 ID로 한다.

## 6. 대화 내 검색

검색 RPC는 호출자가 볼 수 있는 메시지를 최신부터 복호화하며 대소문자와 공백 차이를 무시한 부분 일치로
거른다. 평문 색인을 만들지 않으므로 비용은 대화의 메시지 수에 비례한다. 한 번에 검사하는 메시지 수와
반환 수에 상한을 두고, 상한에 닿으면 다음 커서를 돌려 이어서 찾게 한다. 검색 결과는 서버와 브라우저
저장소에 남기지 않는다.

## 7. 검증

- pgTAP: grant 부재, 참여 기간에 따른 허용·거부, 1:1 unique, 그룹 인원 상한, 편집 기한, 삭제 후 본문·첨부·반응
  제거, 암호문 열에 평문이 없음, 키 버전 전환, Broadcast topic 권한.
- Vitest: 시각·날짜 구분·묶음 계산, 낙관적 전송과 실패 되돌림, 따라잡기 병합, 이전 페이지 스크롤 보존.
- 수동: [알림 수동 인수 테스트](NOTIFICATION_MANUAL_TESTING.md)의 메시지 전용 절.

## 8. 멘션

기능 명세 §13.22와 §13.17을 구현한다.

- 본문 토큰은 게시물·댓글과 같은 `[@이름](m:<번호>)`이다. 사람은 1번부터 빈틈없이 매기고, 0번은
  `@모든 사람`이다. 토큰 안의 이름은 장식이고 대상은 본문 밖에 둔다. 공개 ID는 바뀌므로 본문에 넣지 않는다.
- 대상은 `private.messages.mention_profile_ids`(배열의 n번째가 n번 토큰)와 `mentions_everyone`에 평문으로
  둔다. 대화 참여자와 같은 메타데이터라 암호화하지 않는다(기능 명세 §13.20). 별도 테이블을 두지 않는 것은
  메시지 한 행 안에서만 뜻이 있고, Push 판정이 메시지 행 하나만 보면 되기 때문이다.
- 전송과 편집은 공개 ID 배열(`p_mention_pub_ids`)을 받고, 서버가 본문을 훑어 쓰인 번호만 해석한다
  (`private.resolve_message_mentions`). 클라이언트가 준 목록을 그대로 믿으면 본문에 없는 사람에게 Push를
  보내게 할 수 있다. 새로 부르는 사람은 지금 멤버여야 하고, 편집이면 그 메시지를 볼 수 있는 멤버(보낸 시각
  전에 들어온 멤버)여야 한다. 편집에서 이미 불려 있던 사람은 나갔어도 그대로 둔다. 1:1 대화의 토큰, 짝 없는
  번호, 한 사람에게 준 두 번호는 거절한다. 공개 ID를 보내지 않는 이전 버전 화면의 편집은 같은 번호가 부르던
  사람을 그대로 이어받는다.
- 멘션의 이름은 토큰에 적힌 글자다. 화면은 보낼 때 후보 목록에 보이던 이름(대화 별명이 있으면 별명)을 토큰에
  적고, 뒤에 별명이나 프로필 이름이 바뀌어도 바꾸지 않는다(기능 명세 §13.22). 읽기 RPC는
  `mention_profile_ids`와 `mentions_everyone`을 함께 돌려주고, 화면은 참여자 목록에서 그 사람의 프로필만
  찾는다. 대상을 모르면 평범한 글자로 그린다. `m:0`은 `mentions_everyone`일 때만 `@모든 사람`으로 그린다.
  이 기능 전에 같은 글자를 직접 쳐 둔 메시지가 있다.
- 대화 목록 미리보기, 답장 원문, 검색 결과, Push 본문은 서버가 토큰을 그 글자 그대로의 `@이름`으로 바꿔
  준다(`private.message_plain_text`). 개명한 사람의 예전 멘션은 새 이름으로 검색되지 않는다. 잘라 낸 뒤에
  바꾸면 토큰이 반쪽 나므로 바꾼 뒤에 자른다. 클라이언트의 복사와 낙관적 답장 인용도 같은 글자를 쓴다
  (`messagePlainText()`).
- 알림 단계는 기존 `muted_until`(끄기)에 `mentions_only`를 더한 세 단계다. `끄기`가 앞선다. 큐잉과 발송 직전
  확인이 같은 판정(`private.member_wants_message_push`)을 쓴다. 기존 `set_conversation_muted`는 단계를
  모르는 이전 버전 화면을 위해 남기고, 새 화면은 `set_conversation_notification_level`을 쓴다.
- 편집으로 새로 불린 멤버에게만 다시 큐잉한다. 같은 메시지와 구독의 delivery는 unique라서, 이미 그 메시지
  Push를 받았거나 대기 중인 멤버에게는 다시 가지 않는다. 발송 직전 확인의 읽음 조건도 그대로 적용된다.

## 9. 대화 별명

기능 명세 §13.25를 구현한다.

- 별명은 `private.conversation_nicknames`(대화·사람마다 한 행)에 둔다. 클라이언트 권한은 없고, 정하고 지우는
  것은 `set_conversation_nickname`만 한다. 정하는 사람과 대상 모두 그 그룹의 지금 멤버여야 한다. 같은 값이면
  아무것도 쓰지 않아 시스템 메시지도 남지 않는다.
- 나간 멤버의 행은 지우지 않는다. 나간 사람의 지난 메시지에도 같은 이름을 그리고, 다시 들어오면 그대로 쓴다.
  `withdraw_account`는 그 사람에게 붙은 별명을 모두 지운다.
- `list_conversations`의 참여자마다 `nickname`이 온다. 화면은 매핑할 때 `name`을 별명 우선의 보이는 이름으로,
  `profileName`을 프로필 이름으로 둔다. 그래서 `.name`을 쓰는 곳은 따로 고치지 않아도 별명을 그리고, 멤버 목록의
  둘째 줄과 별명 시스템 메시지만 `profileName`을 쓴다.
- 서버가 이름을 직접 내려 주는 두 곳은 별명을 join한다. 반응한 사람 목록(`list_message_reactors`)과 그룹 Push
  본문 앞의 발신자(`private.message_push_content`)다.
- 바꾸면 `nickname_set`·`nickname_cleared` 시스템 메시지(`[바꾼 사람, 대상]`, 새 별명)를 넣는다. 메시지 행이
  생기므로 다른 멤버에게는 기존 `message_changed` 신호가 가고, 화면이 대화 목록의 그 대화 한 줄을 다시 읽어
  참여자의 별명이 바뀐다. 시스템 메시지라 Push, 읽지 않은 수, 숨긴 대화 되살리기에 들지 않는다.

## 10. 메시지 전달

기능 명세 §13.26을 구현한다.

- 전용 RPC 없이 기존 전송 흐름을 쓴다. 대상 대화마다 `prepare_message_attachments`로 새 경로를 예고하고,
  Storage `copy`로 원본 object와 축소본을 그 경로에 복사한 뒤 같은 메시지 ID로 `send_message`를 부른다.
  `send_message`는 직접 올린 첨부와 똑같이 복사본의 소유자·크기·MIME type을 확인한다.
- Storage는 복사할 원본을 요청자의 RLS로 읽으므로 `message-attachments` 읽기 정책이 `object.copy`를 허용한다
  (Storage 설계 §4.4). 복사본의 소유자는 요청자이고 쓰기는 업로드 정책을 그대로 거친다.
- 다시 보낼 때 같은 메시지 ID가 이미 저장됐으면 `prepare_message_attachments`가 `23505`로 거부하고, 클라이언트는
  복사를 건너뛴 채 `send_message`로 저장된 메시지를 받는다. 복사본이 이미 있다는 응답은 복사 성공으로 본다.
- 첨부 이름은 화면이 이미 복호화한 원본 이름을 다시 예고해 새 키로 암호화한다.
