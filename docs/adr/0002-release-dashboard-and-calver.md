# 릴리즈 대기 목록 이슈, `/release` 릴리즈 PR, CalVer 태그

**상태**: 채택 · **날짜**: 2026-11-10

`dev` → `main` 릴리즈는 운영자가 PR을 손으로 열고, 무엇이 나가는지와 릴리즈 후 할 일(공지,
prod 시크릿·변수·Dashboard 설정)을 각 PR 본문에서 직접 찾아야 했다. 그래서 고정 이슈 하나가
prod에 아직 나가지 않은 변경(마지막 릴리즈 태그...`dev`)을 계속 보여 주고, 저장소 admin이 그
이슈에 `/release`를 남기면 GitHub App 토큰으로 `dev`를 head로 한 릴리즈 PR을 연다. prod
배포가 성공하면 그 커밋에 한국 날짜 CalVer 태그(`vYYYY.M.D`, 같은 날은 `.2`부터)를 달고, PR
본문의 `## 릴리즈` 절과 변경 파일에서 모은 항목을 체크리스트 이슈로 연다. 배포는 그대로
`release.yml`이 맡는다. 현재 절차는 [환경 가이드 §5.5](../DOCKER.md#55-릴리즈-대기-목록과-릴리즈-pr)에 있다.

## 검토한 대안

- **semver**: 이 앱은 사용자가 버전을 고르지 않는 정적 SPA이고, 이 앱에 의존하는 외부 코드도
  없다. major/minor 판단의 기준이 없어 숫자만 의미 없이 오르고, bump 수준을 정하는 장치도 따로
  필요하다. 날짜는 workflow가 기존 태그만 보고 정할 수 있고 장애 시점과도 바로 이어진다. 0을
  채우지 않는 것은 semver 파서와 호환되게 하기 위해서다. 스토어 배포나 공개 API가 생기면 그쪽에만
  별도 버전을 붙인다.
- **`GITHUB_TOKEN`으로 PR 생성**: 저장소 설정상 Actions가 PR을 만들 수 없고, 허용하더라도
  `GITHUB_TOKEN`이 연 PR에는 `pull_request` workflow가 돌지 않아 릴리즈 PR에 CI가 빠진다.
- **PAT**: 토큰이 개인 계정과 그 계정의 모든 저장소 권한에 묶인다. App은 이 저장소와 Contents
  읽기·Pull requests 쓰기로 범위를 좁힐 수 있다.
- **release-please 같은 릴리즈 도구**: Conventional Commits와 changelog 파일을 전제로 한다.
  이 저장소의 PR 제목 규칙과 맞지 않고, prod 설정 할 일을 모을 방법도 없다.
- **스냅샷 `release/*` 브랜치**: PR을 연 뒤 `dev`가 움직여도 내용이 고정되지만, main의 merge
  commit을 관리할 브랜치가 하나 더 생긴다. `release.yml`이 이미 stale release를 거부하고 PR 본문이
  `dev` head와 배포 결과를 보여 주므로 `dev`를 그대로 head로 쓴다.
- **대기 목록을 `main...dev`로 계산**: 릴리즈 PR을 merge한 뒤 배포가 실패하면
  그 변경이 prod에 없는데도 목록에서 사라진다. 태그는 배포가 성공한 커밋에만 생기므로 태그를 기준으로
  삼는다.
- **`/release`를 write 권한자에게 허용**: write 권한자도 dev→main PR을 직접 열 수는 있지만, 릴리즈를
  시작하는 공식 경로는 prod 책임자에게 둔다. 그래서 admin으로 좁힌다.
- **트리거로 특정 계정 멘션이나 이슈 체크박스 사용**: 멘션은 계정 이름에 묶인다. 체크박스는
  workflow가 이슈 본문을 다시 쓸 때마다 사라진다. 슬래시 명령은 권한 확인만 하면 된다.
- **할 일을 라벨로 분류**: 라벨만으로는 "무엇을 할지"를 담을 수 없어 결국 본문을 읽어야 한다.
  템플릿을 저장소가 관리하므로 `## 릴리즈` 절의 `- 공지:`·`- 할 일:` 줄을 읽는다.
- **외부 채널(Discord 등)로 공지 발송**: 이번에는 이슈 정리까지만 한다. 공지 문구는 사람이 다듬는다.

## 영향

- `issue_comment`·`workflow_run`은 기본 브랜치의 workflow를 실행하므로, 이 workflow와
  `scripts/release/`의 변경은 `main`에 릴리즈된 뒤부터 적용된다. 도입 자체도 첫 릴리즈 이후부터다.
- 태그는 `release.yml`이 성공한 커밋에만 생기므로, 태그 목록이 곧 prod에 나간 커밋 목록이다.
