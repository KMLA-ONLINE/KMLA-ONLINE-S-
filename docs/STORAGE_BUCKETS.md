# Supabase Storage 버킷 설계

## 1. 문서 목적

이 문서는 KMLA Online에서 사용하는 Supabase Storage 버킷의 이름, 책임, 파일 정책, 수명주기 및 보안 경계를 정의한다.

## 2. 기본 원칙

- 모든 버킷은 private으로 생성한다.
- 버킷은 화면이나 이미지 슬롯의 수가 아니라 접근 권한과 보안 경계를 기준으로 나눈다.
- 프로필 사진과 커버처럼 접근 정책이 같은 자산은 같은 버킷에 저장하고 object path로 용도를 구분한다.
- 데이터베이스에는 만료되는 signed URL이 아니라 버킷 이름과 object path를 저장한다.
- 클라이언트는 현재 사용자의 권한을 확인한 뒤 private object에 접근한다. 클라이언트 화면의 권한 검사는 보안 경계로 사용하지 않으며 실제 권한은 Storage RLS와 데이터베이스 정책에서 강제한다.
- 사용자가 입력한 원본 파일 이름이나 익명 작성자를 식별할 수 있는 값을 object path에 노출하지 않는다.
- 기존 목업의 `space-*` 명칭은 사용하지 않고 현재 제품 용어인 `group`을 사용한다.
- 모든 메시지 첨부는 클라이언트에서 암호화하되 1:1 대화와 그룹 대화는 서로 다른 버킷에 저장한다.

## 3. 버킷 목록

| 버킷                         | 저장 대상                   | 주요 접근 경계                                                       |
| ---------------------------- | --------------------------- | -------------------------------------------------------------------- |
| `profile-media`              | 프로필 사진, 프로필 커버    | 프로필 소유자가 관리하고 해당 프로필을 볼 수 있는 사용자가 열람      |
| `group-media`                | 그룹 아이콘, 그룹 커버      | 그룹 소유자와 관리자가 관리하고 해당 그룹을 볼 수 있는 사용자가 열람 |
| `post-attachments`           | 게시물 사진, 일반 첨부 파일 | 그룹 또는 개인 게시물의 실제 열람 권한을 가진 사용자가 열람          |
| `direct-message-attachments` | 1:1 메시지의 암호화된 첨부  | 두 대화 참여자가 암호문에 접근하고 클라이언트에서 복호화             |
| `group-message-attachments`  | 그룹 메시지의 암호화된 첨부 | 해당 시점에 허용된 그룹 대화 멤버가 클라이언트에서 복호화            |

## 4. 버킷별 규칙

### 4.1 `profile-media`

- 프로필 사진과 프로필 커버를 함께 저장한다.
- 두 이미지 슬롯은 object path에서 구분한다.
- 사용자는 자신의 이미지만 등록, 변경 및 제거할 수 있다.
- 탈퇴 시 프로필 이미지 object를 제거한다.

### 4.2 `group-media`

- 그룹 아이콘과 그룹 커버를 함께 저장한다.
- 두 이미지 슬롯은 object path에서 구분한다.
- 그룹 소유자와 관리자만 이미지를 등록, 변경 및 제거할 수 있다.
- 공개 그룹을 찾는 사용자와 그룹 멤버 등 그룹 정보를 볼 수 있는 사용자에게 이미지를 제공한다.
- 그룹의 공개 범위와 삭제 상태를 Storage 읽기 정책에도 반영한다.

### 4.3 `post-attachments`

- 게시물의 사진과 일반 파일을 함께 저장한다.
- 첨부 metadata와 표시 순서는 데이터베이스에서 관리한다.
- 그룹 게시물 첨부는 해당 게시물에 접근할 수 있는 그룹 멤버만 열람할 수 있다.
- 전체 공개 개인 게시물 첨부는 승인 사용자 전체가 열람할 수 있다.
- 비공개 개인 게시물 첨부는 작성자 본인만 열람할 수 있다.
- 익명 게시물과 실명 게시물의 작성자를 연결해 추론할 수 없도록 object path에 업로더의 사용자 ID를 넣지 않는다.
- Storage INSERT는 현재 사용자가 작성자인 게시물의 `pending` 첨부 행에 기록된 정확한 bucket과 path에만 허용한다.
- 클라이언트에는 게시물 Storage object의 직접 UPDATE와 DELETE를 허용하지 않으며 upsert를 사용하지 않는다.
- 첨부 metadata의 직접 INSERT, UPDATE 및 DELETE를 허용하지 않고 작성자 권한을 확인하는 RPC로만 변경한다.
- 게시물 또는 개별 첨부가 삭제되면 연결된 object도 정리한다.

### 4.4 `direct-message-attachments`

- 1:1 대화의 첨부만 저장한다.
- 클라이언트는 첨부 내용과 원본 파일 이름을 업로드 전에 암호화한다.
- Storage에는 암호문만 저장하며 정해진 위협 범위의 서버와 운영자는 저장된 원본 내용과 원본 파일 이름을 읽을 수 없어야 한다.
- 업로드 대상이 1:1 대화인지 데이터베이스에서 확인하고 그룹 대화의 첨부 업로드를 거부한다.
- 두 대화 참여자만 연결된 암호문에 접근할 수 있다.
- 대화 참여자, 파일 형식, 암호화 전 크기 및 이미지 가로·세로는 암호화하지 않는다.
- 암호화 형식과 버전을 식별하는 정보는 원본 파일 이름과 분리해 관리한다.

### 4.5 `group-message-attachments`

- 그룹 대화의 첨부만 저장한다.
- 클라이언트는 첨부 내용과 원본 파일 이름을 업로드 전에 암호화한다.
- Storage에는 암호문만 저장하며 정해진 위협 범위의 서버와 운영자는 저장된 원본 내용과 원본 파일 이름을 읽을 수 없어야 한다.
- 업로드 대상이 그룹 대화인지 데이터베이스에서 확인하고 1:1 대화의 첨부 업로드를 거부한다.
- 대화 참여자, 파일 형식, 암호화 전 크기 및 이미지 가로·세로는 암호화하지 않는다.
- 신규 멤버는 참여 이후에 전송된 첨부만 복호화할 수 있다. 참여 이전 object를 내려받을 수 있더라도 해당 암호화 키는 제공하지 않는다.
- 1:1 대화와 같은 암호문 형식을 사용하되 별도의 버킷과 epoch 키 생명주기를 사용한다.

## 5. Object Path

| 버킷                         | Path 형식                                   |
| ---------------------------- | ------------------------------------------- |
| `profile-media`              | `{user_uuid}/{avatar\|cover}/{object_uuid}` |
| `group-media`                | `{group_uuid}/{icon\|cover}/{object_uuid}`  |
| `post-attachments`           | `{post_uuid}/{object_uuid}`                 |
| `direct-message-attachments` | `{conversation_uuid}/{object_uuid}`         |
| `group-message-attachments`  | `{conversation_uuid}/{object_uuid}`         |

- 모든 식별자는 UUID를 사용한다.
- object path는 확장자 없는 무작위 `object_uuid`로 끝난다.
- 사용자가 입력한 원본 파일 이름은 path에 사용하지 않는다.
- 게시물 첨부 path에는 그룹이나 작성자 사용자 ID를 넣지 않는다. 공통 `post_uuid`만 사용해 그룹 익명 작성자와 실명 작성자를 연결할 수 없게 한다. 업로더는 `storage.objects.owner_id`로 검증한다.
- 메시지 첨부의 버킷은 데이터베이스에 기록된 대화 유형과 일치해야 한다.
- 기존 object를 덮어쓰지 않는다. 이미지나 첨부를 교체할 때 새 path를 연결한 뒤 이전 object를 정리한다.

## 6. 파일 정책

### 6.1 버킷 제한

`MiB`는 1,048,576바이트를 뜻한다. 배포 환경은 Supabase Pro 프로젝트를 기준으로 한다.

| 버킷                         | Object 최대 크기 | Storage MIME 정책          |
| ---------------------------- | ---------------- | -------------------------- |
| `profile-media`              | 4MiB             | `image/webp`만 허용        |
| `group-media`                | 4MiB             | `image/webp`만 허용        |
| `post-attachments`           | 30MiB            | 모든 MIME type 허용        |
| `direct-message-attachments` | 31MiB            | `application/octet-stream` |
| `group-message-attachments`  | 31MiB            | `application/octet-stream` |

Bucket 제한은 object 하나에 적용되는 최종 방어선이다. 이미지 종류별 제한은 클라이언트가 검사하고, 암호화 전 메시지 파일 제한은 클라이언트가 제출한 metadata와 암호문 길이의 일관성을 finalize RPC가 검사한다. 데이터베이스와 일반 API는 메시지 평문 자체를 검사할 수 없다.

### 6.2 이미지 입력

- JPEG, PNG 및 WebP만 입력으로 받는다.
- 입력 파일은 최대 30MiB 및 50메가픽셀이다.
- GIF, SVG 및 HEIC는 받지 않는다.
- 원본 이미지는 보존하지 않는다.
- 모든 입력 이미지는 클라이언트에서 EXIF 등 metadata를 제거하고 WebP로 다시 인코딩한다.
- 원본보다 큰 해상도로 확대하지 않는다.

### 6.3 이미지 출력

| 용도                     | 긴 변 최대 | WebP 품질 | 최종 크기 상한 |
| ------------------------ | ---------- | --------- | -------------- |
| 프로필 사진, 그룹 아이콘 | 512px      | 0.85      | 1MiB           |
| 프로필 커버, 그룹 커버   | 2400px     | 0.85      | 4MiB           |
| 게시물 사진, 메시지 사진 | 3072px     | 0.85      | 8MiB           |

최종 크기 상한은 품질을 반복해서 낮추기 위한 목표가 아니다. 정해진 해상도와 품질로 한 번 변환한 결과가 상한을 넘으면 업로드를 거부한다.

### 6.4 일반 파일과 미디어

- 게시물과 메시지는 파일 형식을 제한하지 않는다.
- 게시물의 비이미지 파일은 최대 30MiB다.
- 메시지의 비이미지 일반 파일, 오디오 및 동영상은 암호화 전 최대 30MiB다.
- 메시지 안에서 재생할 수 있는 오디오는 MP3, M4A, OGG, WAV 및 WebM이다.
- 메시지 안에서 재생할 수 있는 동영상은 MP4, WebM 및 MOV다.
- 정규화된 WebP 이미지와 위 오디오·동영상 allowlist만 앱 안에서 표시하거나 재생한다.
- 그 밖의 모든 파일은 MIME type과 확장자를 신뢰하지 않고 미리보기 없이 다운로드로만 제공한다.
- 메시지 미디어는 복호화 후 magic bytes가 허용 형식과 일치하는지 클라이언트에서 확인한 뒤 통제된 MIME type의 Blob으로 만들어 재생한다.

## 7. 데이터베이스 Metadata

프로필과 그룹의 단일 이미지 슬롯에는 object path만 저장한다. 버킷은 컬럼의 도메인으로 고정한다.

게시물은 단일 `posts` 테이블에 저장하고 `kind` 값으로 `group`과 `profile`을 구분한다. 댓글, 답글, 반응 및 첨부는 모두 `posts.id`를 참조한다.

공통 컬럼은 다음과 같다.

- 게시물 UUID
- 종류: `group` 또는 `profile`
- 화면에 공개할 작성자 프로필 ID
- 본문
- 본문 형식 버전
- 그룹 UUID
- 타임라인 당사자 UUID
- 제목
- 카테고리 UUID
- 작성 신원
- 공개 범위
- 고정 정보
- 생성·게시·수정·삭제 정보

실제 작성자는 `private` schema의 별도 관계에 저장하고 클라이언트 역할에 해당 관계의 권한을 부여하지 않는다. 실명 게시물만 공개 게시물 행에 화면 표시용 작성자 프로필 ID를 저장하며, 익명 및 운영진 명의 게시물은 이 값을 저장하지 않는다.

첨부 업로드를 시작하려면 부모 게시물 UUID가 먼저 필요하므로 게시 전 내부 행은 `published_at`을 `NULL`로 저장한다. 이 상태는 사용자용 임시 저장 기능이 아니며 일반 조회에 노출하지 않는다. 본문 또는 준비된 첨부가 하나 이상인지 확인한 뒤 게시할 때 `published_at`을 기록하고, 피드 정렬과 화면의 작성 시각에는 `published_at`을 사용한다.

본문 형식 버전 `1`은 `CONTENT_FORMATTING.md`의 `Markdown v1`을 뜻한다. 데이터베이스는 지원하는 버전만 허용하며 생성 RPC는 클라이언트가 임의의 형식 버전을 저장하지 못하게 한다.

종류별 CHECK 제약은 다음 조건을 강제한다.

- 그룹 게시물은 그룹 UUID와 제목 및 작성 신원을 사용하고 타임라인 당사자와 공개 범위를 사용하지 않는다.
- 개인 게시물은 타임라인 당사자와 `public` 또는 `private` 공개 범위를 사용하고 그룹, 제목, 카테고리, 익명·운영진 신원 및 고정 정보를 사용하지 않는다.
- 개인 게시물의 작성 신원은 항상 실명이다.
- 비공개 개인 게시물은 작성자와 타임라인 당사자가 같은 경우에만 허용한다.
- 타인이 작성한 개인 게시물은 전체 공개만 허용한다.
- 게시물 생성 후 `kind`는 변경할 수 없다.

타임라인 타인 작성 허용 값은 프로필에 `true`를 기본값으로 저장한다. 타인 개인 게시물 생성은 하나의 RPC 또는 동등한 원자적 DB 작업에서 타임라인 당사자의 승인 상태와 현재 타인 작성 허용 값을 다시 확인한다.

종류별 조회를 위해 그룹·작성 시각, 공개 개인 글·작성 시각, 타임라인 당사자·작성 시각에 partial index를 둔다.

게시물 및 메시지 첨부 metadata에는 다음 정보가 필요하다.

- 첨부 UUID
- 부모 게시물 또는 메시지 UUID
- object path
- 표시 순서
- MIME type
- 암호화 전 파일 크기
- 이미지 가로 및 세로 크기
- 업로드 상태: `pending`, `ready` 또는 `deleted`
- 생성 시각

게시물 첨부의 원본 파일 이름은 평문으로 저장한다. 메시지 첨부의 원본 파일 이름은 암호문으로만 저장하고 암호화 버전을 함께 기록한다. 메시지 첨부에는 `storage_bucket`을 명시하며 대화 유형과 일치하는지 데이터베이스에서 강제한다. 메시지 이미지의 가로·세로, MIME type 및 암호화 전 크기는 암호화하지 않는다.

파일 해시와 중복 제거 정보는 저장하지 않는다.

## 8. 업로드와 정리

### 8.1 첨부 업로드

1. 클라이언트가 공통 `post_uuid` 또는 메시지 UUID를 기준으로 RPC를 호출해 `pending` 첨부 행과 무작위 UUID path를 만든다.
2. 클라이언트가 지정된 path에 object를 업로드한다. upsert는 사용하지 않는다.
3. 클라이언트가 finalize RPC를 호출한다.
4. RPC가 bucket, path, `storage.objects.owner_id`, object 크기, 기록된 MIME type, 현재 사용자의 권한 및 대화 유형을 검사한다. 게시물 첨부의 생성·교체·순서 변경·개별 삭제는 게시물 작성자에게만 허용한다.
5. 메시지 첨부는 제출된 평문 크기가 종류별 상한 이하인지 검사하고, 이 값에 AES-GCM overhead 29 bytes를 더한 값이 실제 object 크기와 같은지 검사한다.
6. 검증을 통과하면 첨부를 부모 게시물 또는 메시지에 연결하고 상태를 `ready`로 변경한다.

프로필과 그룹 이미지는 별도 첨부 행을 만들지 않는다. 새 UUID path에 업로드한 뒤 finalize RPC가 검증하고 이미지 슬롯의 path를 교체한다.

SQL RPC는 object의 실제 바이트가 WebP인지, 이미지의 실제 치수가 맞는지, 암호화된 평문의 MIME type과 크기가 맞는지 확인할 수 없다. 이 값은 접근 권한 판단에 사용하지 않으며, 클라이언트는 표시 직전에 실제 디코딩 결과나 magic bytes를 다시 확인한다. 악의적인 클라이언트가 거짓 metadata를 제출해도 bucket의 object 크기 상한은 넘을 수 없다.

브라우저에 `service_role` 등 Storage 관리용 비밀 키를 노출하지 않는다.

### 8.2 삭제와 고아 Object

- 첨부를 삭제하면 행을 즉시 제거하지 않고 상태를 `deleted`로 변경한다.
- 매일 한 번 정리 작업이 48시간 이상 지난 `pending` 첨부, `deleted` 첨부 및 48시간 이상 연결되지 않은 프로필·그룹 이미지를 삭제한다.
- 정리 작업은 Storage object를 삭제한 뒤 해당 첨부 행을 제거한다.
- 일시적인 삭제 실패는 다음 일일 정리에서 다시 시도한다.
- 정리 대상 object는 실제 삭제까지 최대 약 72시간 남을 수 있다.

## 9. 파일 접근

- 모든 버킷은 private이며 Storage SELECT RLS에서 실제 도메인 접근 권한을 검사한다.
- 게시물 첨부 RLS는 `posts.kind`와 해당 행의 그룹·타임라인·공개 범위를 확인해 그룹 멤버십, 승인 사용자 전체 공개 또는 작성자 전용 접근을 적용한다.
- 클라이언트는 권한 검사 후 유효 시간 1시간의 signed URL을 발급받아 파일을 표시하거나 다운로드한다.
- signed URL은 유효 시간 동안 URL을 가진 사람이 사용할 수 있는 bearer 링크로 취급한다.
- 사용자가 파일 접근 권한을 잃어도 이미 발급된 signed URL은 남은 유효 시간 동안 사용할 수 있다. 최대 잔여 접근 시간은 1시간이다.
- 데이터베이스에는 signed URL을 저장하거나 캐시하지 않고 bucket과 object path만 저장한다.
- 여러 파일을 표시할 때는 권한 검사를 유지한 batch signed URL 발급 방식을 사용한다.

## 10. 메시지 클라이언트 암호화

### 10.1 목적과 범위

메시지 암호화의 목적은 데이터베이스, Storage 및 운영 로그에 저장된 값을 직접 조회하는 관리자가 메시지 본문, 첨부 내용 및 첨부 원본 파일 이름을 읽지 못하게 하는 것이다. 클라이언트가 업로드 전에 암호화하고 내려받은 뒤 복호화하며, 데이터베이스와 Storage에는 암호문만 저장한다.

대화 키는 데이터베이스 밖의 Edge Function 비밀 키로 보호한다. 따라서 이 설계는 서버가 키를 전혀 알 수 없는 종단간 암호화가 아니라, 저장 데이터 직접 조회를 방어하는 클라이언트 암호화다.

다음 공격은 범위에 포함하지 않는다.

- Edge Function의 비밀 환경 변수 또는 배포 권한을 가진 관리자
- 배포된 클라이언트 코드를 악의적으로 변경하는 관리자
- 데이터베이스의 멤버십, epoch 또는 암호문을 능동적으로 변조하는 관리자
- 클라이언트 기기 또는 로그인 세션 탈취
- 대화 참여자가 자신에게 제공된 키나 복호화한 내용을 외부에 복사하는 행위

학생 운영자에게는 데이터베이스 조회에 필요한 최소 권한만 부여하고 Edge Functions, 비밀 환경 변수 및 배포 설정에는 접근 권한을 부여하지 않는다. 마스터 키를 데이터베이스, SQL 함수, Supabase Vault, 클라이언트 번들 또는 운영 로그에 저장하지 않는다.

### 10.2 Edge Function 키 브로커

- Edge Function 비밀 환경 변수에 별도로 생성한 256-bit 마스터 키를 저장한다.
- 키 브로커는 사용자 JWT를 검증하고, 사용자 권한으로 조회한 대화 및 epoch 접근 관계를 통해 요청자가 해당 키를 받을 수 있는지 확인한다.
- 새 대화나 그룹 멤버 변경 시 Edge Function이 무작위 256-bit epoch 키를 만들고 마스터 키로 AES-256-GCM 봉인한 뒤 암호문만 데이터베이스에 저장한다.
- epoch 키 봉인에는 매번 무작위 12-byte nonce를 사용하고 epoch UUID와 형식 버전을 AAD에 포함한다.
- 키 브로커는 권한을 확인한 참여자에게 필요한 epoch 키를 TLS 응답으로 제공하며 메시지 본문이나 첨부 평문은 받지 않는다.
- 클라이언트는 받은 epoch 키를 메모리에만 보관하고 새로고침하면 다시 요청한다. 로그아웃이나 세션 폐기 시 메모리의 키를 제거한다.
- 사용자 비밀번호는 메시지 키 생성이나 봉인에 사용하지 않는다. 비밀번호 변경과 초기화는 기존 메시지 복호화 가능 여부를 바꾸지 않는다.
- 함수 요청과 오류 로그에는 마스터 키, epoch 키, 메시지 평문 또는 복호화된 파일 이름을 기록하지 않는다.
- Edge Function은 멤버십 변경 권한을 직접 검증한 뒤 서버 전용 데이터베이스 작업으로 멤버십과 새 epoch를 하나의 트랜잭션에 반영한다.

### 10.3 대화 Epoch 키

- 1:1 대화와 그룹 대화는 각각 무작위 256-bit epoch 키를 사용한다.
- epoch 키는 사용자별 envelope를 만들지 않고 Edge Function 마스터 키로 한 번만 봉인해 저장한다.
- 그룹 대화는 최대 100명까지 참여할 수 있다.
- 그룹 멤버 추가, 자발적 탈퇴 또는 강제 퇴장 때 새 epoch를 만든다.
- 시간 기반 정기 회전은 하지 않는다.
- epoch별 접근 관계에는 해당 시점의 대화 멤버를 기록한다. 키 브로커는 이 관계에 포함된 사용자에게만 봉인을 해제한 키를 제공한다.
- 새 멤버는 가입과 함께 생성된 epoch부터 접근하고 이전 epoch 키는 받지 않는다.
- 탈퇴하거나 내보내진 멤버는 참여 당시 epoch 키를 다시 요청할 수 있지만 탈퇴와 함께 생성된 새 epoch 키는 받지 못한다.
- 멤버십과 epoch 변경은 대화 행을 잠근 하나의 상태 전이로 직렬화한다. 새 epoch 저장과 멤버십 변경이 함께 성공하지 않으면 모두 취소한다.
- 메시지 생성 RPC는 현재 active epoch만 허용한다. 멤버 변경과 동시에 이전 epoch로 전송한 메시지는 거부하고 클라이언트가 새 키를 요청해 다시 암호화한다.
- 대화에 참여하지 않은 앱 관리자가 멤버를 강제 퇴장시켜도 Edge Function이 새 epoch를 생성하므로 별도의 `rekey_required` 상태나 남은 멤버의 키 배포 절차가 필요하지 않다.

### 10.4 암호문 형식

- 메시지 본문, 첨부 파일 이름 및 첨부 내용은 active epoch 키로 AES-256-GCM 암호화한다.
- 각 암호화 작업은 무작위 12-byte nonce를 새로 사용한다.
- 암호문 v1 형식은 version 1 byte, nonce 12 bytes, ciphertext 및 인증 태그 16 bytes다. 전체 크기는 평문보다 29 bytes 크다.
- 첨부는 나누지 않고 파일 전체를 한 번에 암호화한다. 빈 파일은 허용하지 않는다.
- AAD에는 암호문 용도를 나타내는 고정 문자열과 대화 UUID, epoch UUID 및 메시지 또는 첨부 UUID를 포함한다.
- 메시지를 편집할 때 같은 epoch 키를 사용하더라도 새 nonce를 사용한다. 같은 key와 nonce 조합은 다시 사용하지 않는다.
- 메시지를 다른 대화로 전달할 때 기존 암호문이나 Storage object를 복사하지 않는다. 클라이언트에서 복호화한 뒤 새 메시지·첨부 UUID와 대상 대화 키로 다시 암호화하고 업로드한다.
- 메시지 암호문과 epoch 키 봉인 형식은 각각 버전을 저장하며 기존 버전의 복호화 지원 없이 새 버전으로 전환하지 않는다.
